# STACKS Game Math

This guide describes the active local demo, not a production gambling backend or
an approved platform submission. The source of truth is
[`math.mjs`](../../stacks-3d-home/math.mjs), with round orchestration in
[`main.js`](../../stacks-3d-home/main.js).

For the separate server-driven upload export, including its nine validated target modes,
see the [Stake Engine guide](../stake-engine/README.md).

## Round Contract

1. Select a stake of at least 1.00 demo credit, within the available balance.
2. Select a target from 1.50x to 39.00x in 0.01x increments in the local demo.
3. Starting a round deducts the stake once and samples its outcome once.
4. The tower reveals the complete result. Reaching the target triggers a cue,
   but does not settle the round or credit the balance yet.
5. A result at or above the target wins, including an exact tie. The return is
   the stake multiplied by the selected target. A lower result returns zero.

This is a target-prediction game. The active game does not offer manual cash-out
during the reveal. A result higher than the target does not increase the payout.

## Outcome Distribution

Let `N = 2^32 = 4,294,967,296` and `r = 0.965`. The browser obtains a uniformly
distributed unsigned 32-bit integer `word` using `crypto.getRandomValues`.

```text
rawResult = r * N / (word + 1)
result = min(rawResult, 1000)
```

The raw result remains unrounded until settlement. Display/history values are
floored to two decimal places using `multiplierUnits(value)`. Rounding the raw
outcome before comparing it to the target would change the game contract.

The minimum raw result is 0.965x, so some rounds break before 1x. Values such as
0.73x in old mockups or synthetic UI fixtures are not generated by this formula.
All raw results above 1000x are revealed as 1000x.

For target `x = u / 100`, where `u` is the integer target in hundredths, the
probability helper returns:

```text
P(win at u) = floor(965 * N / (10 * u)) / N
           approximately 0.965 / x
```

Examples calculated with the current helpers; probabilities below are rounded:

| Selected target | Win probability | Return on a winning 100.00 stake |
| --- | --- | --- |
| 1.50x | 64.333333% | 150.00 |
| 2.50x | 38.600000% | 250.00 |
| 3.00x | 32.166667% | 300.00 |
| 7.00x | 13.785714% | 700.00 |
| 25.00x | 3.860000% | 2,500.00 |
| 39.00x | 2.474359% | 3,900.00 |

Before cent rounding, expected return divided by stake is `P(win) * x`,
approximately 96.5%. The finite sample space and payout rounding make the exact
return slightly lower. This is a long-run expectation, not a promised return
for an individual player or session. Changing the target changes win frequency,
not the approximate theoretical return.

## Money And Settlement

Wallet values and stakes are represented in integer cents. Targets are integer
hundredths: `250` means 2.50x. `payout` uses integer `BigInt` arithmetic:

```text
winningReturnCents = floor(stakeCents * targetUnits / 100)
losingReturnCents = 0
closingBalance = openingBalance - stakeCents + returnCents
netProfitCents = returnCents - stakeCents
```

The return includes the original stake. For a 100.00 stake with a 2.50x target,
a 4.49x result returns 250.00, a net profit of 150.00. A 1.76x result returns
zero, a net loss of 100.00. A 1.01 stake winning at 1.25x returns 1.26 after
cent rounding, not 1.27.

`resolveRound(current, crash, target)` returns `null` while the reveal is still
below its final result. It settles at the final result even when an animation
frame jumps over it. `settle` only runs its balance update while the round is
in the `running` phase.

## Bonus Stages And Turbo

| Reveal multiplier | Stage | Current effect |
| --- | --- | --- |
| Below 1.50x | Stacking | Base presentation |
| 1.50x and above | Stack Bonus | Stage color/effects and block-count change |
| 3.00x and above | Double Stack | Higher stage and faster reveal |
| 7.00x and above | Super Stack | Higher stage and faster reveal |
| 25.00x and above | Legendary Stack | Legendary presentation |

These stages are reached deterministically by multiplier thresholds. They are
not independently sampled bonus events. Win celebration tiers are selected from
the player's target, not the maximum multiplier revealed.

`BONUS_STAGES` also defines factors `1`, `1.05`, `1.1`, `1.2`, and `1.5`.
The exported `effectiveMultiplierUnits` helper can apply factors, and has unit
tests, but **the active frontend does not call it for settlement**. It pays
`payout(stakeCents, multiplierUnits(selectedTarget))`. Do not advertise those
factors as extra winnings. Enabling them would require a new math design and
return analysis.

Turbo changes the reveal speed from a base rate of `0.14` to `0.36`. Neither
Turbo, visual randomness, music, nor frame rate changes the sampled outcome or
payout formula.

## Autoplay And Replay

Autoplay samples a fresh outcome for each round and uses the same target-payout
contract. It accepts 1-100 rounds and positive profit/loss limits. Stop limits
are checked against the session's net balance change after settlement, so the
last round may cross a limit. Stopping autoplay prevents subsequent rounds;
it does not cancel or refund the round already running.

[`replay.mjs`](../../stacks-3d-home/replay.mjs) stores a versioned snapshot with
`roundId`, `betCents`, `targetUnits`, `resultUnits`, `payoutCents`, `won`,
`visualSeed`, `turbo`, and `bonusTransitions`. Replays use these saved values;
they do not resample an outcome, debit/credit the balance, or add a history entry.

History retains up to 30 rounds in memory; it is lost on reload. Replay preserves
the recorded result and selections, but is not a frame-by-frame recording of
physics or audio. The raw unrounded outcome is not stored in the snapshot.

## Verification And Production Boundary

From the repository root:

```sh
node --test stacks-3d-home/math.test.mjs stacks-3d-home/replay.test.mjs
```

Tests cover distribution boundaries, payout rounding, helper factors, ties,
instant breaks, reveal completion, the cap, and replay snapshot validation.
They do not constitute independent certification.

In demo mode, the browser controls both the outcome and the demo wallet. The
separate Engine export includes an RGS adapter and compressed math files; its
real platform integration, capacity, and approval remain unverified. A static
frontend deployment alone is not an approved real-money release.
